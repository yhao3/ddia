# 原文翻譯

多年來，PostgreSQL 一直是支撐 ChatGPT 和 OpenAI API 等核心產品最關鍵的底層資料系統之一。隨著用戶群快速增長，資料庫的需求也呈指數級增長。過去一年，我們的 PostgreSQL 負載增長超過 10 倍，且仍在快速攀升。

我們為維持這種增長而推進生產基礎設施的努力，揭示了一個新見解：PostgreSQL 可以被擴展到可靠支援比許多人先前認為可能的更大規模讀取密集型工作負載。這個系統（最初由加州大學伯克利分校的科學家團隊創建）使我們能夠透過單一主要節點（primary）的 [Azure PostgreSQL 彈性伺服器實例](https://learn.microsoft.com/en-us/azure/postgresql/overview)和近 50 個分佈在全球多個區域的[[ch5#領導者與追隨者|讀取副本]]來支援大規模全球流量。這是我們如何透過嚴格優化和扎實工程將 PostgreSQL 擴展到每秒數百萬次查詢以支援 8 億用戶的故事；我們也將分享沿途學到的關鍵經驗。

## 初始設計的裂痕

ChatGPT 發布後，流量以前所未有的速度增長。為了支撐它，我們快速在應用程式和 PostgreSQL 資料庫層實施了大量優化，透過增加實例大小進行垂直擴展（scale up），並透過添加更多[[ch5#領導者與追隨者|讀取副本]]進行水平擴展（scale out）。這個架構長期以來運作良好。透過持續改進，它繼續為未來增長提供充足的空間。

單一主節點架構能滿足 OpenAI 規模的需求聽起來可能令人驚訝；然而，讓這在實踐中運作並不簡單。我們曾多次看到由 PostgreSQL 過載引起的嚴重事故（SEV），它們通常遵循相同的模式：上游問題導致資料庫負載突然飆升，例如快取層故障導致的大規模快取未命中、昂貴的多表 JOIN 查詢使 CPU 飽和、或新功能上線引發的寫入風暴。隨著資源使用率攀升，查詢延遲上升，請求開始逾時。重試進一步放大負載，觸發惡性循環，有可能使整個 ChatGPT 和 API 服務降級。

![[v1/openai_vicious_cycle.svg]]
**圖：負載下的惡性循環**

雖然 PostgreSQL 對於我們的讀取密集型工作負載擴展良好，但在高寫入流量期間我們仍然遇到挑戰。這主要是由於 PostgreSQL 的[[ch7#實現快照隔離|多版本併發控制（MVCC）]]實現，這使其對寫入密集型工作負載效率較低。例如，當查詢更新一個元組甚至單一欄位時，整行都會被複製以創建新版本。在高寫入負載下，這會導致顯著的**寫入放大**。它也增加了**讀取放大**，因為查詢必須掃描多個元組版本（死元組）以檢索最新版本。MVCC 還引入了其他挑戰，如表和索引膨脹、增加的索引維護開銷，以及複雜的 autovacuum 調優。（你可以在我與卡內基美隆大學 Andy Pavlo 教授合寫的部落格 [*The Part of PostgreSQL We Hate the Most*](https://www.cs.cmu.edu/~pavlo/blog/2023/04/the-part-of-postgresql-we-hate-the-most.html) 中找到對這些問題的深入探討，該文被[引用](https://en.wikipedia.org/wiki/PostgreSQL#cite_note-37)於 PostgreSQL 維基百科頁面。）

## 將 PostgreSQL 擴展到每秒數百萬次查詢

為了緩解這些限制並減少寫入壓力，我們已將可[[ch6|分區]]的寫入密集型工作負載遷移（並繼續遷移）到分片系統如 Azure Cosmos DB，並優化應用程式邏輯以最小化不必要的寫入。我們也不再允許向當前的 PostgreSQL 部署添加新表。新工作負載預設使用分片系統。

即使我們的基礎設施已經演進，PostgreSQL 仍然保持未分片狀態，單一主要實例服務所有寫入。主要原因是對現有應用程式工作負載進行分片將非常複雜且耗時，需要更改數百個應用程式端點，可能需要數月甚至數年。由於我們的工作負載主要是讀取密集型，且我們已實施大量優化，當前架構仍提供充足的空間來支援持續的流量增長。雖然我們不排除未來對 PostgreSQL 進行分片，但鑑於我們為當前和未來增長準備的充足空間，這不是近期優先事項。

在以下章節中，我們將深入探討我們面臨的挑戰和實施的大量優化，以解決它們並防止未來中斷，將 PostgreSQL 推向極限並擴展到每秒數百萬次查詢（QPS）。

### 減少主節點負載

*挑戰：只有一個寫入者，單一主節點設置無法擴展寫入。嚴重的寫入峰值可能快速使主節點過載並影響 ChatGPT 和 API 等服務。*

解決方案：我們盡可能減少主節點的負載——包括讀取和寫入——以確保它有足夠的容量來處理寫入峰值。讀取流量盡可能被卸載到[[ch5#領導者與追隨者|副本]]。然而，有些讀取查詢必須保留在主節點上，因為它們是寫入[[ch7|交易]]的一部分。對於這些，我們專注於確保它們高效並避免慢查詢。對於寫入流量，我們已將可分片的寫入密集型工作負載遷移到分片系統如 Azure CosmosDB。較難分片但仍產生高寫入量的工作負載需要更長時間遷移，該過程仍在進行中。我們還積極優化應用程式以減少寫入負載；例如，我們修復了導致冗餘寫入的應用程式錯誤，並在適當的地方引入延遲寫入以平滑流量峰值。此外，當回填表欄位時，我們強制執行嚴格的速率限制以防止過度的寫入壓力。

### 查詢優化

*挑戰：我們在 PostgreSQL 中識別出幾個昂貴的查詢。過去，這些查詢的突然量增會消耗大量 CPU，減緩 ChatGPT 和 API 請求。*

解決方案：一些昂貴的查詢，例如連接多個表的查詢，可能會顯著降級甚至使整個服務崩潰。我們需要持續優化 PostgreSQL 查詢以確保它們高效並避免常見的[[ch3#交易處理還是分析？|線上事務處理（OLTP）]]反模式。例如，我們曾識別出一個極其昂貴的查詢連接了 12 個表，該查詢的峰值是過去高嚴重性 SEV 的原因。我們應盡可能避免複雜的多表連接。如果連接是必要的，我們學會了考慮分解查詢並將複雜的連接邏輯移至應用程式層。許多這些有問題的查詢是由物件關係映射框架（ORM）生成的，因此仔細審查它們產生的 SQL 並確保其行為符合預期非常重要。在 PostgreSQL 中找到長時間運行的空閒查詢也很常見。配置如 `idle_in_transaction_session_timeout` 等逾時對於防止它們阻塞 autovacuum 至關重要。

### 單點故障緩解

*挑戰：如果一個讀取副本宕機，流量仍可路由到其他副本。然而，依賴單一寫入者意味著存在單點故障——如果它宕機，整個服務都會受影響。*

解決方案：大多數關鍵請求只涉及讀取查詢。為了緩解主節點的單點故障，我們將這些讀取從寫入者卸載到副本，確保即使主節點宕機，這些請求仍可繼續服務。雖然寫入操作仍會失敗，但影響減少了；由於讀取仍然可用，這不再是 SEV-0。

為了緩解主節點故障，我們在[[ch5#處理節點宕機|高可用性（HA）]]模式下運行主節點，配備熱備援（hot standby）——一個持續同步的副本，隨時準備接管服務流量。如果主節點宕機或需要離線進行維護，我們可以快速提升備援以最小化停機時間。Azure PostgreSQL 團隊已做了大量工作以確保這些[[ch5#處理節點宕機|故障轉移]]即使在非常高的負載下也保持安全可靠。為了處理讀取副本故障，我們在每個區域部署多個副本，並有足夠的容量餘裕，確保單一副本故障不會導致區域性中斷。

### 工作負載隔離

*挑戰：我們經常遇到某些請求在 PostgreSQL 實例上消耗不成比例資源的情況。這可能導致運行在同一實例上的其他工作負載效能下降。例如，新功能上線可能引入低效查詢，大量消耗 PostgreSQL CPU，減緩其他關鍵功能的請求。*

解決方案：為了緩解「吵鬧鄰居」問題，我們將工作負載隔離到專用實例上，以確保資源密集型請求的突然峰值不會影響其他流量。具體來說，我們將請求分為低優先級和高優先級層級，並將它們路由到不同的實例。這樣，即使低優先級工作負載變得資源密集，也不會降低高優先級請求的效能。我們對不同產品和服務也應用相同的策略，以便一個產品的活動不會影響另一個產品的效能或可靠性。

### 連線池

*挑戰：每個實例都有最大連線限制（Azure PostgreSQL 為 5,000）。很容易耗盡連線或累積過多空閒連線。我們之前曾發生過由連線風暴導致所有可用連線耗盡的事故。*

解決方案：我們部署 PgBouncer 作為代理層來池化資料庫連線。以 statement 或 transaction 池化模式運行它允許我們有效地重用連線，大大減少活動客戶端連線數。這也減少了連線建立延遲：在我們的基準測試中，平均連線時間從 50 毫秒降至 5 毫秒。跨區域連線和請求可能很昂貴，因此我們將代理、客戶端和副本共置在同一區域以最小化網路開銷和連線使用時間。此外，PgBouncer 必須仔細配置。像空閒逾時這樣的設置對於防止連線耗盡至關重要。

![[v1/openai_pgbouncer_proxy.svg]]
**圖：PgBouncer 作為 PostgreSQL 代理**

每個讀取副本都有自己的 Kubernetes 部署，運行多個 PgBouncer pods。我們在同一個 Kubernetes Service 後面運行多個 Kubernetes deployments，該服務在 pods 之間進行負載均衡。

### 快取

*挑戰：快取未命中的突然峰值可能觸發對 PostgreSQL 資料庫讀取的激增，使 CPU 飽和並減緩用戶請求。*

解決方案：為了減少 PostgreSQL 的讀取壓力，我們使用快取層來服務大部分讀取流量。然而，當快取命中率意外下降時，快取未命中的爆發可能將大量請求直接推向 PostgreSQL。這種資料庫讀取的突然增加消耗大量資源，減緩服務。為了防止快取未命中風暴期間的過載，我們實現了快取鎖定（和租約）機制，以便只有在特定鍵上未命中的單一讀取者從 PostgreSQL 獲取資料。當多個請求在同一快取鍵上未命中時，只有一個請求獲取鎖並繼續檢索資料和重新填充快取。所有其他請求等待快取更新，而不是同時都打到 PostgreSQL。這顯著減少了冗餘的資料庫讀取，並保護系統免受級聯負載峰值的影響。

### 擴展讀取副本

*挑戰：主節點將預寫日誌（WAL）資料流式傳輸到每個讀取副本。隨著副本數量增加，主節點必須向更多實例傳輸 WAL，增加網路頻寬和 CPU 的壓力。這導致更高且更不穩定的[[ch5#複製延遲問題|副本延遲]]，使系統更難可靠地擴展。*

解決方案：我們在多個地理區域運營近 50 個讀取副本以最小化延遲。然而，在當前架構下，主節點必須向每個副本流式傳輸 WAL。雖然它目前在非常大的實例類型和高網路頻寬下擴展良好，但我們不能無限添加副本而最終不會使主節點過載。為了解決這個問題，我們正與 Azure PostgreSQL 團隊合作開發[級聯複製](https://www.postgresql.org/docs/current/warm-standby.html#CASCADING-REPLICATION)，其中中間副本將 WAL 中繼到下游副本。這種方法允許我們在不使主節點不堪重負的情況下擴展到可能超過一百個副本。然而，它也引入了額外的操作複雜性，特別是在故障轉移管理方面。該功能仍在測試中；在將其推廣到生產環境之前，我們將確保它是健壯的並能安全地進行故障轉移。

![[v1/openai_cascading_replication.svg]]
**圖：PostgreSQL 級聯複製**

### 速率限制

*挑戰：特定端點的突然流量峰值、昂貴查詢的激增或重試風暴可能快速耗盡關鍵資源如 CPU、I/O 和連線，導致廣泛的服務降級。*

解決方案：我們在多個層面實施速率限制——應用程式、連線池、代理和查詢——以防止突然的流量峰值壓垮資料庫實例並觸發級聯故障。避免過短的重試間隔也至關重要，這可能觸發重試風暴。我們還增強了 ORM 層以支援速率限制，並在必要時完全阻止特定的查詢摘要。這種有針對性的負載卸載形式能夠從昂貴查詢的突然激增中快速恢復。

### Schema 管理

*挑戰：即使是小的 schema 更改，例如更改欄位類型，也可能觸發[完整表重寫](https://www.crunchydata.com/blog/when-does-alter-table-require-a-rewrite)。因此我們謹慎應用 schema 更改——限制為輕量級操作並避免任何重寫整個表的操作。*

解決方案：只允許輕量級 schema 更改，例如添加或刪除不會觸發完整表重寫的某些欄位。我們對 schema 更改強制執行嚴格的 5 秒逾時。允許並發創建和刪除索引。Schema 更改僅限於現有表。如果新功能需要額外的表，它們必須在替代的分片系統（如 Azure CosmosDB）中而不是 PostgreSQL。當回填表欄位時，我們應用嚴格的速率限制以防止寫入峰值。雖然這個過程有時可能需要超過一週，但它確保了穩定性並避免任何生產影響。

## 結果與未來之路

這項工作證明，透過正確的設計和優化，Azure PostgreSQL 可以擴展到處理最大的生產工作負載。PostgreSQL 為讀取密集型工作負載處理每秒數百萬次查詢，為 OpenAI 最關鍵的產品如 ChatGPT 和 API 平台提供動力。我們添加了近 50 個讀取副本，同時保持[[ch5#複製延遲問題|複製延遲]]接近零，在地理分佈的區域維持低延遲讀取，並建立了足夠的容量餘裕以支援未來增長。

這種擴展在最小化延遲和提高[[ch1#可靠性|可靠性]]的同時運作。我們在生產中始終提供低雙位數毫秒的[[ch1#描述效能|p99 客戶端延遲]]和五個九的可用性。在過去 12 個月中，我們只有一次 SEV-0 PostgreSQL 事故（它發生在 ChatGPT ImageGen [病毒式發布](https://newsletter.pragmaticengineer.com/p/chatgpt-images)期間，當時寫入流量在一週內突然激增超過 10 倍，超過 1 億新用戶註冊。）

雖然我們對 PostgreSQL 帶我們走了多遠感到滿意，但我們繼續推動其極限以確保我們有足夠的空間支援未來增長。我們已經將可分片的寫入密集型工作負載遷移到我們的分片系統如 CosmosDB。剩餘的寫入密集型工作負載更難分片——我們也在積極遷移這些以進一步從 PostgreSQL 主節點卸載寫入。我們也在與 Azure 合作啟用級聯複製，以便我們可以安全地擴展到更多的讀取副本。

展望未來，我們將繼續探索額外的方法來進一步擴展，包括分片 PostgreSQL 或替代的分散式系統，因為我們的基礎設施需求繼續增長。

# 心得：DDIA 理論的實踐驗證

這篇 OpenAI 的技術文章是 DDIA 理論知識在超大規模生產環境中的絕佳實踐案例。以下結合 DDIA 的內容進行分析：

## 複製策略：[[ch5|第五章 複製]]的實踐

OpenAI 採用典型的[[ch5#領導者與追隨者|單主複製]]架構，這正是 DDIA 第五章所描述的最常見複製模式。文章中提到的幾個關鍵點都與 DDIA 內容呼應：

1. **讀取副本擴展**：透過近 50 個[[ch5#領導者與追隨者|讀取副本]]分散讀取負載，這是 DDIA 所說的「讀擴充」策略
2. **[[ch5#複製延遲問題|複製延遲]]控制**：文章強調保持複製延遲接近零，這正是 DDIA 討論的複製延遲問題及其對一致性的影響
3. **[[ch5#處理節點宕機|故障轉移]]機制**：使用熱備援（hot standby）實現高可用，與 DDIA 描述的故障轉移流程一致
4. **級聯複製**：為了進一步擴展副本數量，採用級聯複製減輕主節點壓力，這也是 DDIA 提到的進階複製拓撲

## 分區考量：[[ch6|第六章 分區]]的權衡

有趣的是，OpenAI 選擇**不對 PostgreSQL 進行分區**，而是將可分片的工作負載遷移到 CosmosDB。這完美印證了 DDIA 第六章的觀點：

> 「分片是一個重量級解決方案，主要在大規模場景下才有意義。如果你的資料量和寫吞吐量可以在單臺機器上處理，通常最好避免分片。」

OpenAI 的策略是：
- 讀取密集型工作負載透過複製擴展（scale out via replication）
- 寫入密集型工作負載遷移到原生支援分片的系統

這避免了 DDIA 所警告的分片複雜性，如[[ch6#分區與次級索引|分區與次級索引]]的困難、跨分片交易的挑戰等。

## MVCC 的代價：[[ch7#實現快照隔離|第七章 交易]]的深入理解

文章直接提到 PostgreSQL 的[[ch7#實現快照隔離|多版本併發控制（MVCC）]]實現導致寫入效率低下。這與 DDIA 第七章的討論一致：

- **寫入放大**：每次更新都要複製整行創建新版本
- **讀取放大**：查詢需要掃描多個版本找到最新資料
- **Autovacuum 開銷**：死元組需要定期清理

這解釋了為什麼他們積極將寫入密集型工作負載遷移出去。

## 效能指標：[[ch1#描述效能|第一章 描述效能]]

文章提到「低雙位數毫秒的 p99 客戶端延遲」和「五個九的可用性」。這正是 DDIA 第一章強調的：
- 使用[[ch1#描述效能|百分位數]]（而非平均值）來描述延遲
- 明確定義[[ch1#可靠性|可靠性]]目標

## 快取策略：避免級聯故障

文章描述的快取鎖定機制是經典的「驚群效應」（thundering herd）防護：當快取失效時，只允許一個請求去查詢資料庫，其他請求等待。這與 DDIA 第一章討論的[[ch1#可靠性|容錯]]設計原則一致——系統應該優雅地處理負載峰值而非崩潰。

## 總結

OpenAI 的 PostgreSQL 擴展經驗是一個教科書級的案例研究，展示了如何：

1. 透過[[ch5|複製]]而非[[ch6|分區]]來擴展讀取密集型工作負載
2. 理解並規避[[ch7#實現快照隔離|MVCC]]在寫入密集場景的限制
3. 在多個層面實施防護措施避免級聯故障
4. 使用正確的[[ch1#描述效能|指標]]監控和優化系統

這篇文章最重要的啟示是：**理解你的工作負載特性，選擇最適合的擴展策略**，而非盲目追求最新或最複雜的分散式架構。正如 DDIA 所言，單機能做的事情比許多人想像的要多。
